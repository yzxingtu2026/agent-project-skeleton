# UI 原型图生成

本模块负责从项目上下文分析、Prompt 构造、异步图像生成到前端实施交接的完整 UI 原型工作流。

## 目录

- 适用范围
- 工作流程
- 生成质量标准
- 配置
- 图像任务 CLI
- 前端实施交接
- 降级与排障

## 适用范围

- Web 应用、官网、SaaS 后台、CRM、ERP 和数据看板
- iOS、Android、H5 和小程序界面
- 桌面客户端、插件、编辑器和工具型应用
- 游戏 HUD、菜单、关卡选择和设置页
- 单个组件、弹窗、面板、表单、列表、卡片和图表区

## 工作流程

### 1. 理解目标与现有系统

1. 读取当前仓库中与界面有关的文件和文档，例如 `README.md`、设计规范、现有页面、组件库、样式文件、路由和布局组件。
2. 判断输出类型：完整页面、局部组件、弹窗或抽屉、移动端界面、桌面窗口、游戏界面或设计系统片段。
3. 提取品牌色、字体、组件库、技术栈、目标用户、信息密度、现有交互模式、无障碍和响应式约束。
4. 只在关键缺口会显著改变结果时追问；其余细节根据产品类型和现有代码合理推断。

### 2. 构造生成 Prompt

将用户需求扩展为包含以下信息的图像生成 Prompt：

- 产品背景、业务目标和目标用户
- 平台、画幅和尺寸
- 导航、侧栏、内容区、工具栏、状态区和弹窗层级等区域结构
- 表格、表单、图表、筛选器、按钮、标签、卡片和反馈状态等内容与控件
- 品牌色、明暗主题、信息密度、圆角、阴影、图标和图片使用方式
- 选中、悬停、加载、禁用、校验错误和确认反馈等交互状态
- 跟随用户语言的界面文字；中文项目使用中文

不要把未经验证的固定项目背景写入 Prompt。若用户只要求“做一个后台首页”，先从当前仓库和产品语境推断；无法推断时使用通用 SaaS 后台范式。

### 3. 提升中文文字质量

- 保留用户要求的标题、状态说明、色彩规范、动效说明、适用场景和组件示例，不要通过删除细节掩盖文字生成问题。
- 要求使用常规黑体或无衬线字体、水平排版、高对比、充足行距和留白。
- 避免花体、过细字重、透视或旋转文字、发光描边和复杂文字背景。
- 将详细说明分栏、分块并控制行长；非关键小字可用占位条，但不得删除明确要求的规范项。
- 对品牌名、按钮名和状态标签等关键文案使用 CLI 的 `--exact-text` 参数。
- 默认使用 `--text-density balanced`；规范板使用 `dense`；仅在用户明确要求极简视觉时使用 `minimal`。

### 4. 生成并交付

1. 按本文的“图像任务 CLI”章节启动异步任务并保存 `task_id`。
2. 在有限等待窗口内查询状态；任务完成后取得图片绝对路径并展示。
3. 结合用户反馈迭代 Prompt 或参考图。
4. 用户需要工程方案或代码实现时，按本文的“前端实施交接”章节继续执行。

## 生成质量标准

- 第一屏直接呈现真实产品界面，除非用户明确要求营销落地页。
- 后台和工具产品优先保证信息密度、可扫描性和高频操作效率。
- 消费或品牌页面可以更具视觉表达，但必须保留真实内容和可实现结构。
- 避免用单一色相铺满界面；品牌无明确要求时，不要默认整页紫蓝、深蓝、米色或咖啡色。
- 使用符合平台习惯的图标按钮、分段控件、开关、滑块、菜单、标签页、表格和表单校验。
- 移动端考虑拇指操作区、底部导航、安全区、键盘遮挡和小屏换行。
- 桌面端考虑窗口尺寸、工具栏、侧栏、状态栏、快捷操作和密集表格。
- 游戏 UI 考虑 HUD 层级、暂停和设置、输入方式、可读性与动画暗示。

## 配置

按以下顺序读取配置：当前进程环境变量、用户级配置文件 `~/.config/codex-ui-mockup-gen/config.json`、项目根目录 `.env` 兼容配置。

支持的配置项：

- `OPENAI_API_KEY`：必需，不得要求用户在聊天中粘贴密钥。
- `OPENAI_API_BASE`：OpenAI 兼容 API 地址，默认 `https://api.openai.com/v1`。
- `OPENAI_IMAGE_MODEL`：图像模型名称。
- `OPENAI_UI_OUTPUT_DIR`：默认输出目录，未配置时为 `docs/images/ui-generated/`。
- `UI_GEN_PROJECT_ROOT`：可选的项目根目录覆盖值。

## 图像任务 CLI

### 命令入口

```bash
python .agent/skills/ui-mockup-gen/scripts/generate_mockup.py
```

启动基本任务：

```bash
python .agent/skills/ui-mockup-gen/scripts/generate_mockup.py start \
  --prompt "<UI 需求描述>" \
  --platform web \
  --style "现代、清爽、适合高频业务操作" \
  --audience "运营人员" \
  --language zh
```

带项目上下文或参考图：

```bash
python .agent/skills/ui-mockup-gen/scripts/generate_mockup.py start \
  --prompt "<UI 需求描述>" \
  --context-file docs/design.md \
  --reference-image docs/brand/color.png \
  --reference-image docs/brand/ip.png \
  --output dashboard-home.png
```

也可用 `--reference-dir <目录>` 自动读取目录中的 png、jpg、jpeg 和 webp 文件。

### 参考图模式

- `--reference-mode auto`：默认。有参考图时优先调用 `/v1/images/edits`；多图失败后尝试首图，仍失败则降级到 `/v1/images/generations` 并记录警告。
- `--reference-mode edit`：强制调用 edits；失败时任务失败。
- `--reference-mode generate`：忽略参考图文件，使用纯文本生成。
- `--mask <路径>`：仅用于 edits 模式。

### 常用参数

- `--size 1536x1024`：图片尺寸，默认 `1536x1024`
- `--model <名称>`：覆盖配置中的图像模型
- `--output <文件名>`：自定义输出文件名
- `--output-dir <路径>`：自定义输出目录；相对路径按项目根目录解析
- `--platform web|mobile|desktop|tablet|game|component|other`
- `--style <描述>`、`--audience <描述>`、`--context <约束>`
- `--context-file <路径>`：读取额外上下文
- `--text-density minimal|balanced|dense`
- `--exact-text <关键文案>`：可重复传入
- `--reference-image <路径>`：可重复传入
- `--reference-dir <目录>`
- `--reference-mode auto|edit|generate`
- `--mask <路径>`
- `--language zh|en|...`

需要完整参数时直接执行 `start --help`，不要依赖可能过期的文档副本。

### 任务生命周期

```bash
python .agent/skills/ui-mockup-gen/scripts/generate_mockup.py status <task_id>
python .agent/skills/ui-mockup-gen/scripts/generate_mockup.py result <task_id>
python .agent/skills/ui-mockup-gen/scripts/generate_mockup.py list
```

1. 执行 `start` 并记录 `task_id`。
2. 告知用户任务已启动和预计耗时。
3. 每隔 15 至 30 秒执行 `status`。
4. 最多连续等待约 5 至 8 分钟或查询 10 至 20 次。
5. 状态仍为 `pending` 或 `running` 时停止本轮等待，保留 `task_id`，告知用户下次可继续查询；不要杀死任务或重新启动。
6. 完成后执行 `result`，取得绝对路径并展示图片。
7. 失败时读取任务错误和日志，再按本文的“降级与排障”章节处理。

任务状态和日志保存在系统临时目录 `ui-generation-tasks/`。日志包含任务 ID、输出目录、模型参数、参考图数量、原始提示词、最终提示词、接口降级、保存结果和错误信息。

## 前端实施交接

在 UI 图片完成后，结合当前代码库将视觉结果转化为可执行的工程方案。

### 执行边界

- 用户只要求原型图时，交付图片和必要的设计说明，不修改业务代码。
- 用户要求实施方案时，输出文件、组件、布局、状态和验证计划，不擅自实现。
- 用户明确要求实现时，遵循当前仓库的技术栈、组件库、设计系统和工程规范完成代码修改与验证。

### 反推步骤

1. 检查原型图与当前页面、组件、路由、样式和品牌约束的差异。
2. 列出需要新增或修改的页面、组件、样式、资源和测试文件。
3. 定义组件职责、props、state、事件回调及数据加载边界。
4. 明确 Grid、Flex、响应式断点、桌面布局容器、移动端安全区等布局方案。
5. 判断颜色、字号、间距、图标和组件变体是否应进入设计系统。
6. 覆盖加载、空状态、错误、权限不足、禁用、长文本和窄屏状态。
7. 规划截图、单元测试、交互测试、无障碍检查或视觉回归验证。

### 实施原则

- 将原型图作为视觉参考，不把模型生成的错字、伪控件或不合理交互照搬进代码。
- 优先复用仓库既有组件和样式约定；只在确实减少复杂度时新增抽象。
- 使用真实图标库和结构化组件，不从截图中裁切通用控件。
- 保证核心工作流可操作，并实现目标用户自然预期的状态和反馈。
- 使用稳定尺寸和响应式约束，避免动态内容引发布局跳动或文字重叠。
- 完成后在用户要求的目标视口进行截图或浏览器验证。

## 降级与排障

### 排查顺序

1. 执行 `status <task_id>` 查看结构化状态。
2. 读取状态中记录的错误和日志路径，不凭任务耗时推断失败。
3. 检查 API 地址、模型名、密钥是否存在，以及输出目录是否可写；不得输出密钥内容。
4. 检查服务是否支持 `/v1/images/edits`、多参考图、遮罩和请求尺寸。
5. 用 `start --help` 核对当前脚本参数。
6. 修正配置或参数后再创建新任务；仍在 `pending` 或 `running` 的任务应继续使用原 `task_id`。

### 常见情况

- 缺少 `OPENAI_API_KEY`：指出需要配置的变量或用户级配置文件，不要求用户把密钥发到聊天中。
- edits 不兼容：使用 `--reference-mode auto` 允许脚本逐级降级，或在确认不需要参考图约束时使用 `generate`。
- 任务长时间运行：有限轮询后结束本轮等待并保留 `task_id`，不要终止后台进程。
- 中文细节模糊：优化字体、对比度、分栏和行长，并对关键文案使用 `--exact-text`；不要简单删除用户要求的信息。
- 验证器缺少 PyYAML：这属于验证环境依赖问题；可改用具备依赖的运行时，或同时执行 YAML 人工检查、CLI smoke test 和 `git diff --check`。

### 降级交付

图片生成能力暂不可用时，按用户目标选择最接近的可用结果：

1. 输出结构化文字版 UI 方案。
2. 补充 ASCII 或 Mermaid 布局草图。
3. 当前项目可运行且用户要求实现时，制作可预览的 HTML、CSS 或框架组件原型。
4. 明确说明未生成图片的原因，以及恢复图像生成所需的具体配置或依赖。
